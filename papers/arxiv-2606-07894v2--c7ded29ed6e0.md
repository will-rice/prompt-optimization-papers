# APO-DD: Dialogue Disentanglement via Reflective Optimization of Multi-Component Prompts

Naoki Takada    Tomohiro Okatsu    Yin Min Pa Pa    Katsunari Yoshioka
   Tatsunori Mori Affiliation: Yokohama National University, Japan
Email: [{takada-naoki-xs,mori-tomohiro-bm}@ynu.jp](mailto:)
Email: [{yinminn-papa-jp,yoshioka,tmori}@ynu.ac.jp](mailto:)

###### Abstract

In multi-party chat, interleaved dialogues make it difficult to identify
the context of each utterance. Dialogue disentanglement separates these
dialogues to support dialogue analysis and response generation. Prompt
refinement can improve large language models’ (LLMs’) accuracy on this
task, but manually finding effective prompts for each LLM requires
extensive trial and error. We propose APO-DD, which adapts GEPA to
optimize prompts using execution traces and reflections on failed
decisions. It updates task instructions directly and chat
representations through automatically generated formatting functions. We
compare optimizing either component alone or both. With Qwen3.5-9B, the
best optimized prompt achieves an average score of 68.7 across seven
evaluation metrics on Ubuntu IRC, compared with 57.5 for the best
manually refined prompt. It also outperforms manually refined prompts on
other chat domains without further optimization. For this model,
optimizing task instructions alone does not always improve accuracy over
the initial prompts. Our results suggest that exploring chat
representation as an optimization target may yield higher accuracy than
optimizing task instructions alone. Our code is available at
[https://anonymous.4open.science/r/DB6B](https://anonymous.4open.science/r/DB6B).

## 1 Introduction

Figure 1: An example of dialogue disentanglement. Each dialogue cluster
is shown in a different color.

In multi-party chat, such as Slack and Internet Relay Chat (IRC),
participants discuss different topics in parallel, so dialogues can
become entangled. Such entanglement makes chats difficult to follow. It
also complicates dialogue analysis, because unrelated utterances may be
included in the same context. To address this problem, dialogue
disentanglement was proposed (Elsner and Charniak, 2008). As shown in
Figure 1, dialogue disentanglement partitions an utterance sequence into
coherent dialogue clusters connected by reply-to relations. This task is
an important preprocessing step for downstream applications such as
dialogue state tracking (Ouyang et al., 2020; Jacqmin et al., 2022) and
response generation (Cai et al., 2022; Gu et al., 2022).

Large language models (LLMs) show promise for dialogue disentanglement:
manual prompt refinement enabled Gemini 2.5 Pro (Comanici et al., 2025)
to substantially outperform conventional methods (Takada and Mori,
2026). However, protecting personal information may require local
processing, and processing large amounts of chat data requires
efficiency. These needs motivate improving accuracy with small, locally
runnable LLMs, which still perform poorly (Takada and Mori, 2026).
Prompt refinement offers a promising way to improve the accuracy:
changing how chat data are presented can improve accuracy (Takada and
Mori, 2026). However, effective designs vary across LLMs, requiring a
search for prompts suited to the target model. Conducting this search
manually needs extensive trial and error, motivating automatic prompt
optimization. This leads to the following Research Question:

_How can we automatically optimize prompts to improve disentanglement
accuracy?_

To address this question, we propose APO-DD, an automatic prompt
optimization framework for dialogue disentanglement. There are two LLM
roles: the task LLM, which makes dialogue disentanglement decisions and
whose accuracy we aim to improve, and the optimizer LLM, which updates
the task LLM’s prompt. Motivated by prior work (Section 2.2), we divide
the task LLM’s prompt into two components, the task instruction and the
chat representation, and compare optimizing each component alone or
both. The optimizer LLM proposes a new prompt using execution traces and
reflections on failed decisions. Through repeated updates, we explore
diverse prompts and select the one with the highest validation score as
the optimized prompt. Our contributions are summarized as follows:

- •
  We propose APO-DD, a framework for automatically optimizing dialogue
  disentanglement prompts. With Qwen3.5-9B, the optimized prompt
  outperforms manually refined prompts across topics and chat platforms.
- •
  We show that optimizing task instructions alone does not always
  improve accuracy, highlighting the importance of including chat
  representation in prompt optimization.

## 2 Related Work

### 2.1 Dialogue Disentanglement

Dialogue disentanglement has been studied under several names:
conversation disentanglement (Elsner and Charniak, 2008), chat
disentanglement (Mehri and Carenini, 2017), thread detection (Shen et
al., 2006), and thread extraction (Adams and Martell, 2008). This task
has been approached in two stages. First, each utterance is classified
as starting a new dialogue or replying to a specific utterance within
the preceding context. Second, a clustering algorithm forms dialogue
clusters from these predicted reply-to relations. Early methods inferred
reply-to relations using handcrafted features such as shared words, time
gaps, speaker identities, and user mentions (Elsner and Charniak, 2010).
Later work replaced these features with neural models using RNNs (Mehri
and Carenini, 2017) and LSTMs (Tan et al., 2019). The release of a large
annotated corpus (Kummerfeld et al., 2019) improved neural model
accuracy by providing large amounts of training data. More recently,
incorporating BERT (Devlin et al., 2019) has further improved the
accuracy (Bhukar et al., 2023).

LLMs have also been applied to dialogue disentanglement, but initial
attempts underperformed conventional methods despite their strong
performance across NLP tasks (Brown et al., 2020). First experiments
using GPT-4 (OpenAI et al., 2024a) performed far below conventional
non-LLM methods (Li et al., 2024), and fine-tuned Llama2-7B (Touvron et
al., 2023) did not close this gap (Aselstyne and El Mezouar, 2025). Pal
et al. (2026) found that fine-tuned GPT-4o mini (OpenAI, 2024)
outperformed untuned GPT-4o (OpenAI et al., 2024b), but underperformed
the non-LLM methods. Prompt refinement offers another way to improve
accuracy without changing model weights. Takada and Mori (2026)
demonstrated its effectiveness by manually refining chat
representations. However, the study used simple task instructions and
found that effective prompts differed across LLMs. This leaves room to
explore both task instructions and chat representations for each LLM,
but doing so manually requires extensive trial and error. We therefore
use automatic prompt optimization to explore task instructions and chat
representations and assess their effects on accuracy.

### 2.2 Automatic Prompt Optimization

Recent studies suggest that prompt optimization should consider shared
task instructions and the input representation that varies with each
input. ADO (Lin et al., 2025) uses an additional LLM call to refine
input representations and improve task performance. P3 (Zhang et al., 2025) jointly optimizes shared task instructions and additional
instructions tailored to each input. This study finds that the two types
of instructions interact and that optimizing either alone can be
suboptimal. CFPO (Liu et al., 2025) jointly optimizes prompt content and
format, including input representation and layout, outperforming content
optimization alone. These findings motivate our optimization of two
components: the task instruction and the chat representation.

We next consider how to update these two components. SAMMO (Schnabel and
Neville, 2024) uses separate operations to edit instructions and change
data formats. It outperforms existing prompt optimization methods on
classification tasks. UniPrompt (Juneja et al., 2025) similarly applies
feedback-based edits to individual semantic sections. aPSF (Liu et al., 2026) further shows that updating one semantic factor while keeping the
others fixed is more effective than changing multiple factors in the
same step. Based on these studies, we update only one component at each
step: the task instruction or the chat representation.

Finally, we consider how to update the prompts and retain promising
candidates. OPRO (Yang et al., 2024) uses previous prompts and their
scores, whereas ProTeGi (Pryzant et al., 2023) generates feedback from
errors. Trace (Cheng et al., 2024) uses execution traces to guide
updates. GEPA (Agrawal et al., 2026) combines reflection on execution
traces with Pareto-based selection to optimize multiple prompts and
retain diverse candidates. These studies suggest using LLM outputs and
feedback on errors, not just evaluation scores, to guide prompt updates.
We adopt GEPA because it can optimize multiple prompts and outperformed
several existing prompt optimization methods. Using its framework, we
treat the task instruction and chat representation as separate
optimization targets and update one component at a time.

## 3 APO-DD

### 3.1 Definition of Dialogue Disentanglement

Let the chat data $`C=(u_{1},u_{2},\dots,u_{n})`$ be a chronological
sequence of $`n`$ utterances. Each utterance is represented as
$`u_{i}=(t_{i},s_{i},m_{i})`$, where $`t_{i}`$ is the timestamp,
$`s_{i}`$ is the speaker ID, and $`m_{i}`$ is the message content. The
output is a set of dialogue clusters $`DC=\{d_{1},d_{2},\dots,d_{p}\}`$.
Each cluster $`d_{j}`$ contains utterances that belong to the same
dialogue and are connected by reply-to relations. Dialogue
disentanglement partitions $`C`$ into $`DC`$ so that every utterance
belongs to one cluster, that is, $`C=\bigcup_{d_{j}\in DC}d_{j}`$ and
$`d_{j}\cap d_{k}=\emptyset`$ for all $`j\neq k`$.

### 3.2 LLM-Based Disentanglement

Figure 2: Overview of UA and DA.

We adopt the LLM-based disentanglement framework of Takada and Mori
(2026). The LLM makes one decision for each utterance and we denote the
target utterance of each decision by $`u_{\mathrm{target}}`$. Given
$`u_{\mathrm{target}}`$ and its context, the LLM decides whether it
starts a new dialogue or continues an existing one. If
$`u_{\mathrm{target}}`$ replies to an existing dialogue, the LLM
identifies the utterance or dialogue it replies to, depending on the
assignment method. These decisions are used to construct dialogue
clusters.

There are four assignment methods, as follows. Utterance-level
assignment (UA) selects one preceding utterance as the parent of
$`u_{\mathrm{target}}`$, whereas dialogue-level assignment (DA) selects
one dialogue cluster formed by earlier decisions. Figure 2 illustrates
this distinction. UA and DA use only the context preceding
$`u_{\mathrm{target}}`$. Their extensions, utterance-level assignment
with subsequent context (UA+SC) and dialogue-level assignment with
subsequent context (DA+SC), also provide the utterances following
$`u_{\mathrm{target}}`$ as auxiliary evidence. We use all four methods
because their effectiveness varies across LLMs (Takada and Mori, 2026).

Figure 3: APO-DD optimization cycle. Pareto-based selection chooses a
system $`\Phi`$ from the candidate system pool, and round robin
selection chooses which component to update. In this example, the chat
representation is selected. The optimizer LLM reflects on execution
traces from $`D_{\mathrm{batch}}`$ to update the component. The updated
system is added to the candidate system pool only if its task success
rate on $`D_{\mathrm{batch}}`$ improves.

### 3.3 Scoring Decisions

To assess whether prompt updates are effective during optimization,
APO-DD scores each dialogue disentanglement decision based on the gold
dialogue cluster $`d_{\mathrm{gold}}`$ containing
$`u_{\mathrm{target}}`$. All four assignment methods determine whether
$`u_{\mathrm{target}}`$ starts a new dialogue or continues an existing
one. A decision to start a new dialogue is correct only if
$`u_{\mathrm{target}}`$ is the first utterance in $`d_{\mathrm{gold}}`$.
For a decision to continue an existing dialogue, the scoring criterion
depends on the assignment method. In UA and UA+SC, the selected parent
utterance must precede $`u_{\mathrm{target}}`$ and belong to
$`d_{\mathrm{gold}}`$. In DA and DA+SC, the selected dialogue cluster
must correspond to $`d_{\mathrm{gold}}`$. Each correct decision receives
a score of 1; otherwise, it receives 0.

### 3.4 Prompt Components

APO-DD divides the task LLM’s prompt into two components:
$`P=(p_{\mathrm{task}},p_{\mathrm{chat}})`$. Task instruction:
$`p_{\mathrm{task}}`$ is a text explaining the dialogue disentanglement
task and specifies the evidence used for the decision. Chat
representation: $`p_{\mathrm{chat}}`$ is the target utterance and its
context formatted as text.

### 3.5 Dialogue Disentanglement System

We introduce a chat formatting function $`f_{\mathrm{chat}}`$ to present
$`u_{\mathrm{target}}`$ and its context from $`C`$, producing
$`p_{\mathrm{chat}}=f_{\mathrm{chat}}(C,u_{\mathrm{target}})`$. We
therefore define a dialogue disentanglement system $`\Phi`$ as follows:

```math
\Phi=(p_{\mathrm{task}},f_{\mathrm{chat}})
```

Given chat data $`C`$ and a target utterance $`u_{\mathrm{target}}`$,
$`\Phi`$ applies $`f_{\mathrm{chat}}`$ to obtain $`p_{\mathrm{chat}}`$
and calls the task LLM with $`P=(p_{\mathrm{task}},p_{\mathrm{chat}})`$.

### 3.6 Optimization Cycle

#### Overview

APO-DD follows GEPA, combining reflection-based updates with
Pareto-based candidate selection (Figure 3). Each run uses one
assignment method (Section 3.2) and starts with a seed system using a
minimal prompt. The seed and accepted updates are evaluated on
$`D_{\mathrm{valid}}`$ and added to the candidate system pool. Each
iteration follows the four steps below to update the task instruction or
chat representation. Algorithmic details and prompts are provided in
Appendices A and H.2.

#### (I) Select a System and Component

To select a candidate system for update, we apply Pareto-based selection
using each system’s decision scores on $`D_{\mathrm{valid}}`$
(Section 3.3). First, the systems that attain the maximum score on at
least one utterance in $`D_{\mathrm{valid}}`$ are selected from the
candidate system pool. Next, redundant systems are removed if every
utterance on which they make a correct decision also receives a correct
decision from another remaining system. Then, one system is sampled with
probability increasing with its number of correct decisions on
$`D_{\mathrm{valid}}`$. This strategy preserves systems that perform
well on different validation utterances. Finally, the task instruction
or chat representation is selected as the update target in round robin
order.

#### (II) Collect Execution Traces

The selected system $`\Phi`$ is run with reasoning enabled on each of
the three utterances in a randomly sampled
$`D_{\mathrm{batch}}\subset D_{\mathrm{train}}`$. Each execution trace
records the task LLM input, its final answer, and whether the decision
is correct. If all three decisions are correct, the batch is discarded
and a new batch is sampled. For each incorrect decision, a natural
language reflection is generated by the optimizer LLM from the task
LLM’s execution trace and the gold answer.

#### (III) Propose an Update

For the system and component selected in step (I), the optimizer LLM
proposes an update based on the traces and reflections collected in
step (II). In the following, we use primes to denote updated elements.
For a task instruction update, the proposed instruction text directly
becomes $`p^{\prime}_{\mathrm{task}}`$, producing
$`\Phi^{\prime}=(p^{\prime}_{\mathrm{task}},f_{\mathrm{chat}})`$. For a
chat representation update, the optimizer LLM proposes a representation
to improve the task LLM’s decision accuracy. We instruct the optimizer
LLM to change only the presentation while preserving message text and
candidate IDs, without generating task instructions or adding inferred
information. In an additional call, the optimizer LLM generates
$`f^{\prime}_{\mathrm{chat}}`$ to format chat data according to the
proposal. The generated formatting function is reused at inference time,
so formatting new chat data requires no additional LLM call. The updated
system is
$`\Phi^{\prime}=(p_{\mathrm{task}},f^{\prime}_{\mathrm{chat}})`$.

#### (IV) Verify the Update

$`\Phi^{\prime}`$ is evaluated on the same $`D_{\mathrm{batch}}`$ with
reasoning disabled. If its score exceeds $`\Phi`$’s score from
step (II), it is evaluated on $`D_{\mathrm{valid}}`$ and added to the
candidate system pool with its validation score. Otherwise, it is
discarded.

## 4 Experimental Setup

To evaluate APO-DD, we compare disentanglement accuracy between
optimized systems and those using seed or manually refined prompts. We
also examine the effects of optimization targets and generalization
across datasets and LLMs.

### 4.1 LLM Configuration

We use Qwen3.5-9B (Qwen Team, 2026) as the task LLM because it achieved
the highest AVG with $`\Phi_{\mathrm{manual}}`$ on $`D_{\mathrm{test}}`$
among the evaluated models with $`\leq`$10B parameters (Appendix D.3).
We set temperature to 0. The optimizer LLM is Qwen3.8-Flash (Qiu et al.,
2026), with reasoning disabled and all other parameters left at the API
defaults (temperature=0.7). To analyze generalization across LLMs
(Section 5.4), we evaluate the systems optimized for Qwen3.5-9B with
Gemma-4-12B-it (Google DeepMind, 2026), without further optimization.
Reasoning is disabled for both task LLMs in all benchmark evaluations.

Our best Qwen3.5-9B system runs on a 24 GB RTX 3090 GPU (as detailed in
Appendix B.1).

### 4.2 Optimization Settings

We apply APO-DD separately to each of the four assignment methods
(Section 3.2). The prompts used by the optimizer LLM to propose updates
are based on GEPA’s update prompt (Agrawal et al., 2026) and are
provided in Appendix H.2. We performed one optimization run per
configuration, with a budget of 100k LLM calls fixed before examining
test results. Section 6.2 analyzes how disentanglement accuracy changes
as optimization progresses and discusses the potential for improvement
beyond this budget.

All four assignment methods (Section 3.2) use 50 preceding utterances.
This number is based on our analysis of 47,500 utterances in Ubuntu
IRC’s Train-500msg split (Kummerfeld et al., 2019): 90%, 95%, 99%, and
99.9% of reply relations span at most 11, 17, 49, and 241 utterances,
respectively. The 50 preceding utterances include the utterance being
replied to in approximately 99% of reply relations and span roughly
three times the 95th percentile distance. However, these reply distances
may not generalize to other chat data, and including the parent does not
guarantee sufficient context for a correct decision. UA+SC and DA+SC use
15 subsequent utterances. We chose this number because Takada and Mori
(2026) reported that one model showed its largest improvement under
UA+SC at this length, although the study found no consistent benefit
across LLMs.

### 4.3 Datasets

We use the Ubuntu IRC dataset (Kummerfeld et al., 2019). It contains
real multi-party chat logs of technical discussions about Ubuntu. We use
this dataset for optimization and evaluation as follows.

$`D_{\mathrm{train}}`$ (150 utterances) is randomly sampled from
utterances for which the seed system made incorrect decisions under UA
on the Train-100msg and Channel 2 splits. Each $`D_{\mathrm{batch}}`$
contains three utterances randomly sampled from $`D_{\mathrm{train}}`$.
If all three decisions are correct, the batch is discarded without a
prompt update. To reduce such cases, $`D_{\mathrm{train}}`$ is
restricted to utterances for which the seed system made incorrect
decisions.

$`D_{\mathrm{valid}}`$ (300 utterances) is randomly sampled from the Dev
split (2,500 utterances in 10 samples of 250). Before sampling
$`D_{\mathrm{train}}`$ or $`D_{\mathrm{valid}}`$, we exclude system
messages and utterances annotated as replies to utterances outside the
preceding 50 utterances.

$`D_{\mathrm{test}}`$ (5,000 utterances) contains the entire Test split.
It is used for benchmark evaluation and analysis of the optimization
budget, not for optimization.

To assess generalization across topics and chat platforms, we evaluate
on two additional datasets. IRC New Domains (Gouravajhala et al., 2023)
contains 800 utterances on different topics. Slack Chats (Chatterjee et
al., 2020) contains 3,544 utterances on similar technical topics but
from a different platform.

### 4.4 Evaluated Systems

We evaluate the following dialogue disentanglement systems.
$`\Phi_{\mathrm{seed}}`$ is the initial system for optimization and uses
a minimal prompt. $`\Phi_{\mathrm{opt}}`$ is obtained by optimizing task
instructions alone $`\Phi_{\mathrm{opt}}`$ (task), chat representation
alone $`\Phi_{\mathrm{opt}}`$ (chat), or both components
$`\Phi_{\mathrm{opt}}`$ (both). $`\Phi_{\mathrm{manual}}`$ adapts the
manually refined prompt of Takada and Mori (2026), which achieved high
accuracy. The original manual prompt requests a reason field for each
decision, increasing output length. To reduce generation time, we
replace the original output instructions with a request to output only
the reply target’s ID or new if the target utterance starts a new
dialogue. Prompt examples are provided in Appendix H.1.

### 4.5 Metrics

Following prior studies, we compare predicted and gold dialogue
clusters, focusing on clustering agreement and exact matches. We measure
clustering agreement using Variation of Information (VI) (Meilă, 2007),
Adjusted Rand Index (ARI) (Hubert and Arabie, 1985), One-to-One accuracy
(1-1) (Elsner and Charniak, 2010), and Shen-F1 (S-F) (Shen et al.,
2006). An exact match occurs when a predicted cluster contains exactly
the same utterances as a gold cluster. We measure exact matches using
precision (P), recall (R), and F1 (Kummerfeld et al., 2019). Our main
metric is AVG, the average of these seven scores, with higher values
indicating better performance. All results are averaged over three
evaluation runs with different seeds.

### 4.6 Baselines

We compare $`\Phi_{\mathrm{opt}}`$ with non-LLM and LLM-based methods.
As non-LLM methods, we choose earlier machine learning models:
Elsner (Elsner and Charniak, 2008) and Feedforward+vote (Kummerfeld et
al., 2019); and more accurate BERT based models: DialBERT+conv (Li et
al., 2021), StructuralBERT (Ma et al., 2022), StructuralBERT+DRL (Bhukar
et al., 2023), and DiHRL (Li et al., 2024). For LLM-based methods, we
compare fine-tuned Llama2-7B (Aselstyne and El Mezouar, 2025),
fine-tuned GPT-4o mini (Pal et al., 2026), and
$`\Phi_{\mathrm{manual}}`$ (Takada and Mori, 2026) with Qwen3.5-9B.

## 6 Analysis

We examine the optimized prompts and analyze the optimization budget.

### 6.1 Characteristics of Optimized Prompts

We examine how APO-DD changed the prompt of $`\Phi_{\mathrm{seed}}`$,
focusing on the DA+SC examples in Appendix H.1. The seed task
instruction briefly specifies the task and output format, whereas the
task instruction in $`\Phi_{\mathrm{opt}}`$ (task) includes detailed
rules, examples, and a decision procedure. For example, it directs the
LLM to check prior interactions between speakers and avoid relying
solely on keywords or temporal proximity. Despite these additions,
$`\Phi_{\mathrm{opt}}`$ (task) achieves lower AVG than
$`\Phi_{\mathrm{opt}}`$ (chat) on $`D_{\mathrm{test}}`$ with Qwen3.5-9B.
This suggests that making task instructions more detailed is not always
the best way to improve accuracy.

The seed chat representation groups utterances by dialogue ID and
separates the target and subsequent utterances. $`\Phi_{\mathrm{opt}}`$
(chat) retains this structure but adds participant lists and marks
subsequent utterances as non-selectable context. The optimizer LLM is
instructed to propose updates only to the chat representation and its
explanation, excluding task instructions. Despite these restrictions,
the chat representation in this DA+SC example contained brief task
instructions telling the task LLM to consider semantic links, not just
matching speakers. With this chat representation,
$`\Phi_{\mathrm{opt}}`$ (chat) under DA+SC achieves the highest AVG on
all three datasets in the Qwen3.5-9B experiments. Each of the other
assignment methods also achieves its highest AVG on
$`D_{\mathrm{test}}`$ with $`\Phi_{\mathrm{opt}}`$ (chat) or
$`\Phi_{\mathrm{opt}}`$ (both), rather than $`\Phi_{\mathrm{opt}}`$
(task). These results support exploring chat representation as an
optimization target for dialogue disentanglement.

### 6.2 Optimization Budget

Figure 6: AVG on $`D_{\mathrm{test}}`$ as the optimization budget
increases. Substantial improvements occur up to 80k calls, with little
change from 80k to 100k.

Figure 6 provides a retrospective analysis of AVG on
$`D_{\mathrm{test}}`$ under the preset 100k call budget. At each
checkpoint, we evaluate the system with the highest
$`D_{\mathrm{valid}}`$ score among candidates validated within the call
limit. Most gains occur before 80k calls, with little change from 80k to
100k. This does not imply convergence. In extended runs, a single
improvement on $`D_{\mathrm{valid}}`$ sometimes required roughly 100k
additional LLM calls (Appendix E, Figure A1). Further improvements on
$`D_{\mathrm{valid}}`$ are possible, but optimization until convergence
may be costly. These observations do not identify an optimal budget.
Future work includes exploring larger budgets or achieving high accuracy
with fewer LLM calls.

## 7 Conclusion

We proposed APO-DD, a framework that adapts GEPA for automatic prompt
optimization in dialogue disentanglement. With Qwen3.5-9B and reasoning
disabled, $`\Phi_{\mathrm{opt}}`$ (chat) under DA+SC achieved the
highest AVG among the evaluated settings on all three datasets,
outperforming the best $`\Phi_{\mathrm{manual}}`$ on each without
further optimization. On the main benchmark, $`\Phi_{\mathrm{opt}}`$
(chat) achieved an AVG of 68.7 without fine-tuning, compared with 57.5
for the best $`\Phi_{\mathrm{manual}}`$. The optimized system’s AVG was
also close to the highest reported for the compared non-LLM methods.
These results support exploring chat representation as an optimization
target rather than restricting optimization to task instructions.
However, improvements did not consistently transfer to Gemma-4-12B-it,
and our results do not identify a universally best assignment method or
optimization target. Future work could explore more efficient
optimization with predictable budget requirements. Another direction to
further improve accuracy is supervised fine-tuning with optimized
prompts.

## 8 Limitations

#### GEPA Configuration

We did not systematically tune the optimization budget, the sizes of
$`D_{\mathrm{train}}`$, $`D_{\mathrm{batch}}`$, and
$`D_{\mathrm{valid}}`$, or the numbers of preceding and subsequent
utterances in each prompt. GEPA also allows users to define trace
collection and use. Our configuration enables reasoning during trace
collection but uses final answers, not reasoning text, for reflection
generation and prompt updates. We did not evaluate alternative trace
configurations, and suitable settings may differ across LLMs and chat
data.

#### Variability Across Optimization Runs

We performed only one optimization run per configuration. Each selected
system is evaluated three times. The confidence intervals reflect
variation across these evaluations, not across optimization runs.

#### Scope of Chat Representation Optimization

Although the optimizer LLM is instructed not to include task
instructions in the chat representation, generated chat representations
can contain brief task instruction. We did not evaluate their
contribution separately from formatting changes.

#### Limited LLM Coverage

We optimized prompts only for Qwen3.5-9B, selected because it achieved
the highest AVG with $`\Phi_{\mathrm{manual}}`$ among the evaluated
models with $`\leq`$10B parameters (Appendix D.3). We evaluated transfer
of the optimized systems to Gemma-4-12B-it without further optimization.
Whether optimizing prompts for other LLMs, including larger models,
yields similar improvements remains untested.

#### Comparison with Non-LLM Methods

We compare non-LLM methods using their reported results on
$`D_{\mathrm{test}}`$, as we could not find publicly available trained
models for StructuralBERT, StructuralBERT+DRL, or DiHRL, and found
accessible code only for StructuralBERT (Appendix C). We also could not
find reported results for these baselines on IRC New Domains or Slack
Chats and did not evaluate them on these datasets. Comparisons with
non-LLM methods are therefore limited to $`D_{\mathrm{test}}`$.

#### Potential Pretraining Overlap

All datasets used in this study are publicly available and may have been
included in model pretraining. Our results may therefore not fully
reflect generalization to unseen data.

## 9 Ethical Considerations

We use three publicly available chat datasets: Ubuntu IRC (Kummerfeld et
al., 2019), IRC New Domains (Gouravajhala et al., 2023), and Slack
Chats (Chatterjee et al., 2020). Ubuntu IRC and IRC New Domains are
licensed under CC BY 4.0. Slack Chats is used only for evaluation and is
not redistributed. No private or confidential chat data were used.
Processing independently collected chat data requires careful privacy
protection, as they may contain personal or sensitive information. Such
data should be processed locally, or anonymized before transmission to
an external API.

## Appendix A Detailed Algorithms

The assignment method and ID convention are fixed for each run. If
communication fails, the LLM call is retried without limit. Failed
communication attempts do not increase the call count.

### A.1 Dialogue Disentanglement

Algorithm A1 runs a selected system without prompt updates. The function

converts it to chat text using the selected seed, manual, or optimized
system’s formatter. The displayed context construction applies to seed
and optimized systems: up to 50 preceding utterances and, for UA+SC and
DA+SC, up to 15 subsequent utterances. UA+SC with
$`\Phi_{\mathrm{manual}}`$ may include candidate utterances earlier than
this 50-utterance window. $`C_{\mathrm{pre}}`$ and $`C_{\mathrm{sub}}`$

#### Evaluation and Code Repair

Algorithm A4 processes instances
$`x=(C,u_{\mathrm{target}},DC_{\mathrm{gold}})`$ in stored order, where
$`DC_{\mathrm{gold}}`$ contains the gold dialogue clusters. With
$`\eta=1`$, the task LLM uses reasoning, execution traces are collected,
and the optimizer LLM generates reflections on incorrect decisions. With
$`\eta=0`$, reasoning is disabled for batch verification and validation.
The result $`E=(\mathbf{v},\mathcal{T},\mathcal{F})`$ contains binary
scores, traces, and separate reflections; $`\mathcal{T}`$ and
$`\mathcal{F}`$ are empty when $`\eta=0`$. Here, $`\nu`$ denotes a
binary score and $`\mathbf{1}[\cdot]`$ the indicator function.

TaskLLM$`(P,X,\eta)`$ returns the parsed decision $`\alpha`$ and final
answer text $`y`$. Reflections use $`(P,y,g)`$, and prompt updates use
traces $`(P,y,\nu)`$ together with the reflections.
$`\mathcal{A}_{\mu}(X)`$ contains only IDs of preceding utterances for
UA and UA+SC, or IDs of their dialogue groups for DA and DA+SC. Invalid
outputs are recorded as $`\alpha=\mathsf{FAIL}`$ and scored 0 without
retries. Resolve$`(X,\alpha)`$ returns the utterance $`\hat{u}`$
identified by $`\alpha`$ for UA and UA+SC. For DA and DA+SC, it returns
the original gold dialogue cluster $`\hat{d}\in DC_{\mathrm{gold}}`$
containing the displayed subset identified by $`\alpha`$, not the subset
itself. GoldID$`(X,u_{\mathrm{target}},d_{\mathrm{gold}},\mu)`$ selects
the most recent preceding utterance in $`d_{\mathrm{gold}}`$ among the
displayed candidates. It returns that utterance’s displayed ID for UA
and UA+SC, or the corresponding displayed dialogue ID for DA and DA+SC.
If $`u_{\mathrm{target}}`$ is the first utterance in
$`d_{\mathrm{gold}}`$, it returns new. This value, $`g`$, is passed to
reflection. For UA and UA+SC, scoring also accepts other preceding
utterances in the same gold dialogue cluster.

If chat formatting fails during execution trace collection ($`\eta=1`$),
FailedBatch replaces the entire batch result with zero scores and one
failure trace $`(x,\epsilon,0)`$ per instance, where $`\epsilon`$
describes the formatting failure. ReflectFailure calls the optimizer LLM
once per instance using the current system, the instance, and the error
information. Both lists follow the stored instance order. Thus, all
three scores are 0, and the three failure traces and reflections are
passed to the selected component update. These traces contain error
information, not task LLM outputs. Formatting failures during batch
verification or validation ($`\eta=0`$) instead return
$`\mathsf{FAIL}`$.

Generated chat formatting functions sometimes raised errors, so we
introduced code repair. Code repair changes only the working copy, not a
stored candidate. The flag $`\delta=1`$ indicates repair during the
current Render call. Algorithm A4 first prepares all inputs, storing
$`(x,p_{\mathrm{chat}},X)`$ in the ordered list $`\mathcal{H}`$.
Successful repair clears this list and restarts input preparation on the
entire $`D`$. Only after preparation succeeds are the task LLM calls,
scoring, and decision reflections performed. Unrecoverable formatting
failures follow the failure handling above. Repair during validation
does not repeat batch verification.

#### Scope of Chat Representation Updates

When updating $`f_{\mathrm{chat}}`$, $`p_{\mathrm{task}}`$ remains

## Appendix B Implementation Details

We use GEPA version 0.1.1 without its merge operation (Agrawal et al.,
2026).

For DA and DA+SC, the task LLM input groups preceding utterances by gold
dialogue cluster during execution trace collection, batch verification,
and evaluation on $`D_{\mathrm{valid}}`$. During benchmark evaluation on
$`D_{\mathrm{test}}`$, IRC New Domains, and Slack Chats, these methods
instead use dialogue clusters formed by earlier decisions.

### B.1 Local Inference

Qwen3.5-9B (Qwen Team, 2026) is the primary task LLM.
Gemma-4-12B-it (Google DeepMind, 2026) is used to evaluate the transfer
of systems optimized for Qwen3.5-9B, without further optimization
(Section 5.4). Open-weight LLMs are run locally using vLLM, including
those in Appendix D.3. For optimization and the reported benchmark
results, we used NVIDIA RTX PRO 5000 and RTX 6000 Ada GPUs, each with
48 GB of memory. We set max_model_len to 40,000 tokens during prompt
optimization and 15,000 tokens during benchmark evaluation.

We also verified that $`\Phi_{\mathrm{opt}}`$ (chat) under DA+SC,
optimized with Qwen3.8-Flash and selected at the 100k checkpoint, runs
with Qwen3.5-9B on a single NVIDIA GeForce RTX 3090 GPU with 24 GB of
memory. With 50 preceding and 15 subsequent utterances and reasoning
disabled, the combined input and output length was at most 5,000 tokens
per decision in our evaluation. For this check, we used the original
Hugging Face model in BF16 without quantization, with vLLM’s
max_model_len=10,000 and temperature=0. Our released code and optimized
prompts allow this system to be run without repeating optimization
(Appendix H).

### B.2 Task LLM Settings

For Qwen3.5-9B as the task LLM, we set temperature to 0. All benchmark
evaluations of $`\Phi_{\mathrm{seed}}`$, $`\Phi_{\mathrm{manual}}`$, and
$`\Phi_{\mathrm{opt}}`$ on $`D_{\mathrm{test}}`$, IRC New Domains, and
Slack Chats disable reasoning, including evaluations with
Gemma-4-12B-it.

During optimization, the task LLM uses reasoning for batch evaluation
before prompt updates, with a limit of 2k tokens. Reasoning is disabled
for batch verification and evaluation on $`D_{\mathrm{valid}}`$. When
the reasoning limit is reached, we append the following fixed suffix
before continuing generation, following Yang et al. (2025): Considering
the limited time by the user, I have to give the solution based on the
thinking directly now.\n\</think\>\n\n

### B.3 Optimizer LLM Settings

#### Qwen3.8-Flash

For the experiments in Section 5, we used Qwen3.8-Flash (Qiu et al., 2026) through OpenRouter from September to October 2026. We explicitly
disabled reasoning with reasoning={"enabled":false} and left all other
generation parameters unspecified, using the defaults provided by the
API.

### B.4 LLM Call Counting

The counter $`N`$ counts LLM calls during optimization: task LLM calls
for execution trace collection, batch verification, and evaluation on
$`D_{\mathrm{valid}}`$; optimizer LLM calls for reflections, prompt
updates, code generation, and code repair; and continuation requests
after reasoning is stopped. Code repair calls remain counted when input
preparation restarts.

## Appendix E Optimization Progress

### E.1 Checkpoint Selection

At checkpoints every 20k calls through 100k, we select the candidate
with the highest total score on $`D_{\mathrm{valid}}`$ among those whose
full validation has finished within the call limit. Ties select the
earliest candidate added to the candidate system pool. The 100k
selection is $`\Phi_{\mathrm{opt}}`$ used in the reported results.

### E.2 Validation Beyond 100k Calls

Figure A1 shows decision accuracy on $`D_{\mathrm{valid}}`$ against
cumulative LLM calls with Qwen3.8-Flash as the optimizer LLM and
Qwen3.5-9B as the task LLM. Rows correspond to optimization targets
(task, chat, and both), and columns to assignment methods (UA, UA+SC,
DA, and DA+SC). Blue points represent candidate systems, and orange
lines track the highest score found so far. Some runs improve beyond

\<\|im_start\|\>system

You are given a multi-user chat log where utterances are grouped into
"Previous dialogues" (each labeled with a Dialogue ID) and a single
"Target utterance". Your task is to determine which preceding dialogue
the target utterance responds to, or if it starts a new dialogue.

\*\*Output Format:\*\*

- Output exactly one integer representing the ‘Dialogue ID‘ that the
  target utterance responds to.

- If the target utterance does not respond to any existing dialogue
  (i.e., it initiates a new topic, thread, or interaction stream), output
  the string: ‘new‘.

- Do not provide explanations, JSON, or extra text. Only output the ID
  or "new".

\*\*Guidelines for Analysis:\*\*

1. \*\*Speaker Continuity & Direct Address (Crucial):\*\*

- \*\*Track the Speaker’s Thread:\*\* Identify who sent the target
  utterance. Look for their \*most recent\* interaction in the previous
  dialogues. If the speaker was part of a specific dialogue recently,
  check if the target continues that specific exchange.

- \*\*New Participant Rule:\*\* If the target utterance addresses a
  user who has \*\*not\*\* appeared in any of the provided "Previous
  dialogues", this typically signifies the start of a new interaction
  stream or dialogue, even if the content relates to an ongoing public
  discussion. A bare username mention (e.g., ‘\<UserA\> UserB:‘) without
  semantic content is often a call-out initiating a new sub-thread or
  private-like channel within the room. In such cases, prefer ‘new‘ unless
  there is explicit textual evidence linking it as a direct answer to a
  question posed by ‘UserB‘ in a previous dialogue.

- \*\*Self-Continuation vs. Reply:\*\* If a speaker sends multiple
  messages in a row (or close succession) directed at the same
  person/topic, later messages usually belong to the same dialogue ID as
  the first message in that burst, or extend the most recent dialogue
  involving those two participants. However, if the speaker switches from
  interacting with Person X (in Dialogue A) to addressing Person Y (who
  wasn’t in Dialogue A), this is likely ‘new‘ or a separate thread.

2. \*\*Semantic Coherence vs. Keyword Matching:\*\*

- \*\*Avoid superficial keyword matching.\*\* Just because a word
  appears in both the target and a previous dialogue (e.g., "windows",
  "linux", "error") does not mean they belong together. The \*intent\* and
  \*context\* must align.

- \*\*Topic Introduction Precedes Comparison/Clarification:\*\* A
  common error is linking a follow-up question to the dialogue where the
  main subject was initially verified or defined, rather than the dialogue
  where a \*new option\* or \*alternative\* was introduced.

- \*Example:\* If Dialogue A confirms "File X exists," and Dialogue B
  suggests "Try Alternative Y instead," and the Target asks "Which is
  better, File X or Alternative Y?", the Target belongs to \*\*Dialogue
  B\*\*. The comparison only makes sense because Dialogue B introduced the
  second element. Linking it to Dialogue A ignores the causal link
  provided by the suggestion in B.

- \*\*Clarifications follow constraints:\*\* A clarification question
  (e.g., "on that computer only?") usually follows up on a specific
  constraint mentioned in a prior query by the same speaker or directed at
  them.

- \*\*Interjections and Noise:\*\* An emoticon, short interjection
  (e.g., ":O", "lol", "Yo Yo MA!!!"), or exclamation may be noise or a
  reaction to the immediate visual flow rather than a logical response to
  a technical question.

- \*Exception:\* If the interjection is clearly directed at a specific
  user who just spoke or is the subject of the current active thread
  \*and\* the speaker was already involved in that thread, it belongs to
  that Dialogue ID.

- \*Rule of Thumb:\* If the speaker was NOT part of the main
  conversation thread being discussed (e.g., Lai/Arlie discussing ISPs),
  but speaks to a user who IS in that thread (Lai), check if the speaker
  had a prior mini-interaction with that user. If yes, link to that
  mini-interaction’s dialogue. If no prior interaction exists between
  these two specific users, treat it as ‘new‘ (initiating a fresh
  connection).

3. \*\*Topic Shifts and Non-Sequiturs:\*\*

- If the target utterance introduces a completely new subject, person,
  or observation that has no logical connection to the ongoing discussions
  in the provided dialogues, it is ‘new‘.

- Example: A comment about a user’s nationality amidst a discussion
  about kernel security patches is a non-sequitur and starts a new
  dialogue (‘new‘).

4. \*\*Temporal Proximity:\*\*

- While timestamps help order events, proximity alone is not sufficient
  evidence. A message occurring shortly after another might still be
  unrelated if the speakers and topics do not intersect.

5. \*\*System Messages:\*\*

- Ignore system messages (joins, parts, nick changes) when determining
  conversational threads. They are structural markers, not participants in
  the dialogue logic. Do not assign IDs to system messages.

\*\*Decision Logic Summary:\*\*

1. Identify the \*\*Speaker\*\* of the target utterance.

2. Check if the \*\*Addressee\*\* (if explicitly named) was present in
   the Previous Dialogues.

- If the Addressee is \*\*NEW\*\* (never seen before): Output ‘new‘.

- If the Addressee is \*\*EXISTING\*\*:

- Did the Speaker and Addressee interact in a specific previous
  Dialogue?

You are given a multi-user chat log consisting of several "Previous
dialogues" (each identified by a unique ID and containing multiple
utterances with IDs, timestamps, speakers, and text), a "Target
utterance," and "Subsequent utterances."

Your task is to determine which \*\*preceding dialogue\*\* the Target
utterance responds to. If the Target utterance initiates a completely
new topic or conversation that does not relate to any of the provided
preceding dialogues, you must indicate this.

\*\*Output Format:\*\*

- Output exactly one integer representing the ‘Dialogue ID‘ from the
  "Previous dialogues" section if the target responds to it.

- Output the string ‘new‘ if the target starts a new dialogue.

- Do not output any explanations, JSON structures, or additional text.

\*\*Guidelines for Analysis:\*\*

1. \*\*Explicit Addressing Takes Precedence Over Temporal Proximity:\*\*

- In IRC/chat logs, a prefix like ‘\<Speaker\> Recipient: message‘
  indicates the speaker is directly addressing the recipient. You must
  identify the most recent substantive interaction involving that specific
  \*\*Recipient\*\* in the Previous Dialogues.

- Do not assume a message belongs to a dialogue simply because it
  shares the same timestamp minute as other concurrent conversations. If
  the Target addresses User A, look for User A’s last relevant
  contribution, even if it occurred in a different Dialogue ID than
  messages happening at the exact same second.

- \*Example:\* If the Target is ‘\<Azzie\> Felicia: lol‘, ignore
  Dialogues where Lai is leaving or others are talking, unless Felicia was
  part of those threads. Look specifically for the last meaningful
  statement made by \*\*Felicia\*\*.

2. \*\*Semantic Continuity over Surface Structure:\*\*

- Look beyond literal keyword matching. A response may address the
  \*implication\* or \*context\* of a previous question rather than its
  specific wording.

- Short reactions like "lol", ";)", "thanks", or "owned" are rarely
  standalone new dialogues; they are almost always reactions to the
  immediately preceding joke, insult, or solution provided by the person
  being addressed (or the general flow involving them).

- \*Example:\* If Jesse asks Felicia why she reboots, and Felicia makes
  a joke about toilet flushing, Jesse’s subsequent ‘;)‘ is a closure of
  \*that\* specific banter thread, not a reaction to an unrelated system
  message or a new user entering the room.

3. \*\*Handling Fragmented Messages and Thread Closure:\*\*

- Evaluate the entire stream of the speaker’s immediate messages. The
  Target might be the final punctuation mark (wink, smiley, "nm") closing
  a loop started earlier.

- If a dialogue ends with a question or a humorous remark, and the
  Target provides a direct answer or a laugh tag directed at that specific
  speaker, it belongs to that dialogue.

4. \*\*Distinguishing New Topics (Critical):\*\*

- A "new" classification applies when the Target utterance introduces a
  subject matter entirely unrelated to all preceding dialogues AND lacks
  explicit addressing tags linking it to a prior participant’s open
  thread.

- \*\*Speaker Continuity Bias Warning:\*\* Do NOT assign a reply to a
  dialogue just because the \*same speaker\* participated in that dialogue
  previously. If Speaker X was active in Dialogue ID 5, but then posts a
  message about a completely different topic (e.g., switching from
  technical troubleshooting to quoting a movie scene) without addressing
  anyone in Dialogue 5, it is likely ‘new‘. Explicit addressing (‘Name:‘)
  is the strongest link; semantic continuity is the next strongest. Mere
  presence in a past thread is insufficient.

- System messages (joins/leaves) usually do not constitute a "dialogue"
  that requires a semantic response unless someone explicitly comments on
  the join/leave event itself.

5. \*\*Handling Spam, Noise, and Self-Replies (Critical):\*\*

- \*\*Spam/Trolling:\*\* If a user posts gibberish, random characters
  (e.g., "H", "FG", "GDF"), or disruptive noise that does not form a
  coherent sentence or answer a question, this is generally considered
  ‘new‘ (or noise) rather than a continuation of a valid technical or
  social thread. It breaks the semantic flow of existing dialogues.

- \*\*Self-Reply Fallacy:\*\* A user rarely "replies" to their own
  previous message in a way that links to a \*different\* dialogue ID
  unless they are correcting themselves or continuing a complex thought
  within the \*same\* dialogue block. However, if a user is spamming (see
  above), do not link consecutive spam messages to each other as a
  "dialogue" if they don’t interact with others. More importantly, do not
  assume a short message like "H" is a reply to a previous "H" from the
  same user if that previous "H" was part of a distinct, isolated spam
  burst or if the current context suggests a break in behavior.

- \*Specific Example:\* If Johnathon spams "F", "GDF", "GDH", "FG",
  "H", these are disjointed interruptions. They do not respond to Shenna’s
  kernel compilation questions (Dialogue 10) or Arlie’s frustration
  (Dialogue 19). Therefore, such spam is classified as ‘new‘.

6. \*\*Step-by-Step Reasoning Strategy (Internal):\*\*

1. \*\*Identify the Addressee:\*\* Does the Target contain a ‘Name:‘
   prefix? If yes, note the Name.

1. \*\*Locate the Addressee’s Last Contribution:\*\* Scan Previous
   Dialogues for the most recent message by that Name. Determine which
   Dialogue ID contains that message.

1. \*\*Verify Semantic Fit:\*\* Does the Target content logically react
   to that specific message? (e.g., reacting to a joke, answering a
   question). If the content is totally unrelated (e.g., movie quote vs.
   technical help), reject the link despite the addressee history.

1. \*\*Check for Noise/Spam:\*\* Is the Target part of a gibberish/spam
   stream? If so, and it doesn’t address a specific unresolved query from
   another user, classify as ‘new‘.

1. \*\*Check for Concurrent Noise:\*\* Ignore other dialogues occurring
   at the same timestamp unless they involve the same addressee or the
   Target has no addressee.

1. \*\*Select ID or ‘new‘:\*\* If a clear link exists via addressee AND
   semantics, select that Dialogue ID. If the Target introduces a totally
   new query/topic, is spam, or lacks a semantic bridge to any prior
   thread, select ‘new‘.
