###### Abstract.

AI-integrated applications increasingly rely on large language models
(LLMs), but their intended behavior is not always fully specified by
code. Meaning Typed Programming (MTP) automates prompt construction from
program structure, yet selection criteria, output requirements, and
application policies can remain unstated. We introduce Semantic
Engineering, a methodology for identifying such missing intent and
selectively adding and refining model guidance. We realize this
methodology through Semantic Context Annotations (SemTexts), a dedicated
language mechanism independent of documentation and schema metadata.
SemTexts associate natural-language instructions with individual program
entities and use declaration scopes to determine where they apply. Our
implementation extends the Jac compiler and MTP runtime to preserve
these associations and select applicable guidance during automatic
prompt construction. We evaluate Semantic Engineering on seven
AI-integrated applications and two standard benchmarks across three
models. Across the applications, it achieves a $`5.46\times`$ reduction
in integration lines of code relative to Prompt Engineering while
delivering equal or better task performance in most model–application
settings, reaching up to $`1.83\times`$ the task performance of Prompt
Engineering.

Large Language Models (LLMs) are increasingly integrated into software
applications, including agentic systems (Weber, 2024; Li et al., 2023b;
Beurer-Kellner et al., 2023; Sharma et al., 2025). These applications
use LLMs for tasks such as extracting information, generating text and
code, solving problems, planning, and making decisions. Prompt
Engineering (PE) provides application developers with a direct way to
guide how LLMs perform these tasks (Sahoo et al., 2025). When writing
prompts manually, developers describe the task, provide relevant
context, and specify the expected output. However, these prompts often
repeat information already present in the code, such as field names,
data types, and function interfaces. When developers change these
definitions in the code, they must also update the corresponding
descriptions in their prompts, adding complexity to application
development and maintenance.

Frameworks such as DSPy (Khattab et al., 2023) and NVIDIA
Object-Oriented Agents (NOOA) (Furgale et al., 2026a) reduce manual
prompt construction through programming abstractions and library
interfaces. Meaning Typed Programming (MTP) (Dantanarayana et al., 2025)
provides this support directly within the programming language. Through
the by llm construct, developers express model functionality using
existing code definitions, while the compiler and runtime automate
prompt construction and response handling. The compiler determines which
signatures, types, and identifiers contribute to each model request.
MTP’s evaluation demonstrates a reduction in the number of lines of code
added or modified and the developer time required for LLM integration,
while maintaining or improving task accuracy across the evaluated
benchmarks (Dantanarayana et al., 2025).

However, the information available in code may not fully specify the
intended model behavior. Function signatures and type definitions
describe inputs and outputs, but may leave decision criteria, evidence
requirements, and task policies unspecified. For example, code may
define the available routing options without specifying the criteria for
choosing among them. Such gaps can be addressed through targeted
additions to the model’s prompt that supply the missing intent while
retaining the information already provided by the program. Developers
therefore need a way to express this missing intent in code and include
it in the model’s prompt.

Existing frameworks already let developers selectively supply additional
intent through comments, docstrings, and field descriptions included in
model prompts. TypeChat uses comments in type definitions (Hejlsberg et
al., 2023), while DSPy supports field descriptions through
Pydantic-based signatures (Khattab et al., 2023; DSPy Contributors,
2026). This text may also serve as code documentation or describe schema
fields (Pydantic, 2026), so edits for those purposes can unintentionally
change model behavior even when application requirements remain
unchanged. Also, different functions may call the same LLM-guided
function but require different instructions in the prompt generated for
each call. If annotations are attached only to the shared function’s
definition, developers need separate prompt configurations or context
supplied to the model to specify which instructions apply to each call.
These concerns motivate a dedicated model-guidance channel, independent
of documentation and schema metadata, that lets developers declare
instructions within the workflows where they apply. Using such a channel
selectively requires identifying when code leaves developer intent
unspecified and which code entity the additional guidance should be
attached to, such as a function, type, or parameter.

To inform these choices, we studied AI-integrated applications in § 5 to
assess how selectively supplying intent missing from code affects model
behavior. In the Service Center case study, four routing annotations
increased end-to-end task success from 21.9% to 85.6%; adding two
annotations for required reply facts raised success to 91.0%. The six
selected annotations outperformed full annotation and function-level
docstrings, which achieved 64.7% and 36.8%, respectively. Adding an
annotation that restated the reply composer’s existing purpose provided
only a further 0.2 percentage points. In Task Manager, supplying an
approval requirement before sending email increased end-to-end task
success from 70% to 97%, while leaving routing and reply composition
unannotated. Together, these findings suggest that developers need
support for selectively expressing intent missing from code at relevant
code entities and placing that guidance alongside those entities in
generated prompts.

Our key insight is that a dedicated model-guidance channel, independent
of documentation and schema metadata, should let developers selectively
express intent left unspecified by code at the relevant program entities
and preserve those associations in generated prompts. The compiler binds
each instruction to its target entity, and the runtime places applicable
guidance alongside that entity’s structural information. The channel
also lets developers specify different additional instructions for calls
to the same LLM-guided function, according to each caller’s
requirements.

We introduce Semantic Engineering, an approach that selectively enriches
code with explicit model guidance for behavior left unspecified by code.
This guidance is placed precisely alongside the relevant code entities
in generated prompts. We realize this approach through Semantic Context
Annotations (SemTexts), a language mechanism that extends MTP with
optional model guidance bound to functions, parameters, types, fields,
and enumeration members. Each annotation names its target entity and can
be declared separately from that entity’s definition; its declaration
scope determines which calls can use it.

We implement SemTexts by extending the Jac compiler and MTP
runtime (Mars et al., 2023; Mars, 2025b; Mars, 2025a). The compiler
resolves annotation targets where possible using the program’s scopes
and symbol table, then preserves target references, guidance, and
declaration scopes in an enriched Meaning-Typed Intermediate
Representation (MT-IR) (Dantanarayana et al., 2025). The runtime
completes any required target resolution and selects applicable guidance
independently for each entity using nearest-scope precedence. Relevant
bindings are checked for unresolved targets and duplicate declarations
within the same scope before model invocation. The selected guidance is
placed alongside the corresponding structural information in generated
prompts. The pipeline governs how guidance is associated with program
entities and delivered to model requests; interpreting the
natural-language guidance remains the model’s task.

We evaluate Semantic Engineering against base MTP, Prompt Engineering,
and DSPy on seven AI-integrated applications and two standard benchmarks
across three models. Across the applications, Semantic Engineering
achieves a $`5.46\times`$ reduction in integration LOC relative to
Prompt Engineering while delivering equal or better task performance in
most model–application settings, reaching up to $`1.83\times`$ the task
performance of Prompt Engineering. A separate coding-agent study, using
token consumption as a proxy for cognitive effort, finds that Prompt
Engineering consumes $`1.55`$–$`1.86\times`$ as many tokens as Semantic
Engineering to reach the same development-test performance targets. In
two application case studies, we further examine gradual semantic
enrichment and compare selective enrichment with full annotation and
docstring-based guidance.

## 2. MOTIVATION

In this section, we present a motivating example to examine how
developers express intent in AI-integrated programs. We first compare
how developer intent is conveyed through prompts and code to identify
what code leaves unspecified and where additional guidance is needed. We
then examine existing ways to supply this guidance and their
limitations. Finally, we illustrate language support for expressing
missing intent through a dedicated channel and preserving its
association with relevant code entities in generated prompts.

To ground the discussion, we consider how an AI-Integrated content
generation application selects an agent to handle a user’s revision
request. The application has a planning agent, which determines the
goal, audience, and outline of the content, and a writing agent, which
produces text based on that plan. After reviewing the generated text, a
user may request changes. A routing function examines the current plan
and the user’s request to select which agent should act next: the
planning agent if the plan requires revision, or the writing agent if
the text can be revised within the existing plan.

Using Prompt Engineering, the developer can express the intended routing
policy through the prompt in Figure 2(a). For simplicity, we show only
the task instructions, omitting input serialization, output-format
instructions, and model invocation code. The prompt explains when to
select each agent and directs the model to choose PLANNER when it is
unclear whether the plan needs to change. For example, a request to
“Rewrite this for infrastructure engineers” changes the audience of
content originally planned for first-time users. The policy therefore
selects PLANNER, even though the request asks for rewriting.

### 2.2. What the Code Expresses and What It Leaves Unspecified

We next examine how developer intent expressed through code can guide
the model’s routing decision. We use MTP as the foundation for this
discussion because it provides language-level constructs for model calls
and generates prompts from function signatures and relevant type
definitions (Dantanarayana et al., 2025). These capabilities make MTP a
suitable foundation for exploring a dedicated guidance channel within
the programming language, through which additional instructions can be
associated with code entities and carried into generated prompts.

Figure 2(b) shows an MTP implementation of route_revision, the routing
function that selects an agent to handle the user’s revision request.
The function takes the current plan and revision feedback and returns an
AgentType value identifying the selected agent. The by llm() clause
delegates this routing decision to an LLM, while MTP constructs the
prompt using the program declarations and input values.

Comparing Figures 2(a) and 2(b) shows which parts of the developer’s
intent are represented in code. The function and parameter names
identify the routing task and its inputs, while the return type
identifies the available agents. MTP includes this information in the
generated prompt without requiring the developer to repeat it manually.

However, the selection criteria and ambiguity rule in the manual prompt
are not expressed by these declarations. The code does not specify which
changes require planning, whether planning takes precedence when
feedback also requests rewriting, or how ambiguous feedback should be
handled. Both PLANNER and WRITER satisfy the return type, but only
PLANNER follows the stated policy when the request changes the audience.
These rules express application-specific decisions that the function
signature and enum definition alone do not determine.

The developer therefore needs a way to add the missing instructions
while retaining MTP’s ability to generate prompts from the information
already expressed in code. This raises two questions: which parts of the
intended behavior require guidance beyond what code already expresses,
and at which code entities should that guidance be added?

### 2.3. Expressing and Associating the Missing Guidance

In the example shown in Figures 2(a) and 2(b), the additional guidance
consists of the selection criteria and the rule for ambiguous feedback.
The developer could place these rules in code comments, function
docstrings, or field descriptions. An LLM integration could then include
this text in its generated prompts. For example, a Pydantic field
description can become part of a generated JSON Schema and reach the
model when that schema is included in a request (Pydantic, 2026).

When supplying this guidance, the developer must also decide where each
instruction belongs. The ambiguity rule applies to the routing function,
while each selection criterion describes an individual routing option.
Task instructions and field descriptions, such as those provided by
DSPy (Khattab et al., 2023; DSPy Contributors, 2026), allow the
developer to place the ambiguity rule in the signature’s instructions
and both selection criteria in the description of the agent output
field. In this encoding, both selection criteria are attached to the
agent output field; their associations with PLANNER and WRITER are
expressed within the description’s text. However, as the study
summarized in the introduction shows, the placement of this guidance in
the generated prompt can also affect model behavior. This motivates
support for expressing guidance at the relevant code entities and
preserving those associations during prompt generation.

Reusing existing text channels to express this guidance also raises a
maintenance concern. When comments, docstrings, or field descriptions
serve both ordinary documentation and model guidance, edits made for
documentation can change the model’s instructions. Suppose the agent
field’s description contains the selection criteria and is shared by API
documentation and model requests. Shortening that description to “The
agent selected to handle revision feedback” for documentation purposes
also removes the criteria from the model request, even though the
field’s type and allowed values remain unchanged. The developer
therefore needs to distinguish text maintained as model guidance from
text maintained for documentation.

Different functions may also call the same LLM-guided function but
require different instructions in the prompt generated for each call. If
annotations are attached only to the shared function’s definition,
developers need separate prompt configurations or context supplied to
the model to specify which instructions apply. This motivates allowing
instructions to remain bound to the shared function while limiting their
applicability to calls within a particular caller’s scope.

In this example, developers need to supply the selection criteria and
ambiguity rule while retaining the information already expressed in
code. They also need to express where these instructions belong: the
ambiguity rule applies to the routing function, while the selection
criteria describe the PLANNER and WRITER enum members. These
requirements motivate language support for adding missing guidance
selectively at the relevant entities. A dedicated channel would identify
these instructions as model guidance and allow them to be maintained
independently of ordinary documentation. Prompt generation could then
combine them with the information provided by code, preserving their
associations with the relevant entities. This would let developers
refine the additional guidance while retaining automatic prompt
generation in language-level systems such as MTP.

### 2.4. Semantic Engineering Vision

We envision language support that lets developers express intent not
conveyed to the model by code, independently of documentation and schema
metadata, and associate the additional instructions with the code
entities they describe. In the MTP code in Figure 2(b), the function
signature and enum definition already identify the task, its inputs, and
the available agents. The developer adds the sem declarations shown in
Figure 3 to this program to supply the missing routing policy. These
declarations supplement the existing function and enum definitions.

By expressing guidance at this granularity, developers can refine
individual parts of the routing policy. A change to sem AgentType.WRITER
revises the criterion for selecting that option, while a change to sem
route_revision revises the rule for ambiguous feedback. Prompt
generation carries each revision alongside its associated entity. The
same organization that determines where guidance appears therefore also
gives developers specific places to review and refine how the program
conveys intent to the model. Different functions may also call the same
LLM-guided function but require different instructions in the generated
prompt. For example, standard_workflow and editing_workflow may both
call route_revision, but direct ambiguous feedback to PLANNER and
WRITER, respectively. Figure 6 shows how declarations within each
caller’s scope express these policies while retaining the shared
enum-member guidance.

Building on this support, we envision Semantic Engineering as a
development process for deciding what additional model guidance is
needed, where it belongs, and how to refine it. Developers compare the
application’s routing criteria, output requirements, and policies with
the information already available to the model, then express the missing
requirements at the code entities they describe. Known gaps can be
addressed before execution, while testing helps developers assess the
resulting behavior and determine whether further guidance changes are
needed. This process allows developers to enrich their programs
selectively and gradually while retaining automatic prompt generation.
§ 3 develops this Semantic Engineering workflow.

## 3. Semantic Engineering

We introduce Semantic Engineering as a methodology for selectively
adding model guidance to AI-integrated applications. Algorithm 1
summarizes this methodology. Developers identify requirements not
already conveyed to the model through code, inputs, or existing guidance
(§ 3.1), express those requirements as instructions with explicit target
entities and declaration scopes (§ 3.2), and refine the guidance through
testing and diagnosis (§ 3.3). The first two steps establish the initial
guidance, while the third constitutes gradual semantic enrichment.

### 3.1. Identifying Developer Intent Left Unspecified by Code

To identify developer intent left unspecified by code, the developer
compares the application’s requirements for an LLM-guided operation with
the information expressed through its identifiers, function signature,
and types. The developer then checks whether requirements not expressed
in the code are communicated through the supplied inputs or existing
guidance. Any requirement still unstated needs to be expressed as
natural-language guidance to help the model carry out the operation as
intended. This comparison is the opening step of Algorithm 1.

Consider a developer comparing the application’s requirements with the
code definitions in the revision-routing example (§ 2). The requirements
specify that feedback requiring changes to the plan should be handled by
PLANNER, while feedback requesting only wording changes should be
handled by WRITER. The signature of route_revision and the definition of
AgentType identify the inputs and available agents, but do not express
these rules for choosing between them. If the supplied plan, feedback,
and existing guidance also leave these rules unstated, the developer
identifies them as missing intent. This gap can be identified before
execution, without first observing an incorrect choice.

In this routing example, the return type identifies the available agents
but does not state the criteria for selecting one. Developers can look
for similar omissions in other LLM-guided decisions, including action
selection, approval, and termination. The relevant requirements specify
when an action should be selected, what makes an output acceptable, or
when execution should stop. For example, a Boolean return type for an
approval operation represents acceptance or rejection but does not
specify the conditions for acceptance. Such application-specific
criteria are useful starting points for identifying missing intent
because function signatures and types do not necessarily express them.
The developer can check these requirements against the code, supplied
inputs, and existing guidance to determine which criteria still need to
be expressed through semantic enrichment.

### 3.2. Adding Missing Guidance to Program Entities

For each requirement identified in the previous step, the developer
expresses the missing intent as natural-language guidance that
supplements the information already available to the model. This
guidance can specify a decision criterion, clarify the interpretation of
a value, or state a requirement on an output. In the routing example,
the guidance can state that PLANNER should be selected when feedback
requires changes to the plan.

The developer adds this guidance to the program by associating it with
the entity whose meaning or behavior it clarifies. In the routing
example, the developer associates the rule for resolving ambiguous
feedback with route_revision, because the rule governs how the function
chooses between agents. The criteria for selecting PLANNER and WRITER
are associated with their respective enum members, because they describe
when each option applies. Similarly, an instruction about a parameter’s
interpretation is associated with that parameter, and a requirement on
an output field is associated with that field. These associations guide
the placement of each instruction alongside the corresponding entity in
generated prompts.

When different workflows require different instructions for a shared
function, the developer associates each instruction with that function
and declares it within the lexical scope containing the calls that
should use it. For example, two workflow functions may both call
route_revision but require different rules for ambiguous feedback. The
developer declares each rule within the corresponding workflow
function’s scope, so that both workflows can reuse the same routing
function with the guidance intended for their own calls. These steps
correspond to the first loop in Algorithm 1.

### 3.3. Gradual Semantic Enrichment

After initial enrichment, some application requirements may still not be
conveyed to the model, and some of the added instructions may be
unclear. Gradual semantic enrichment therefore adds a cycle of testing,
diagnosis, and revision to check the resulting behavior and determine
whether additional or revised guidance is needed. This cycle corresponds
to the refinement loop in Algorithm 1.

The developer begins this cycle by running representative tests and
comparing the LLM-guided decisions and application outcomes with the
requirements. When behavior differs from what is expected, the developer
checks for omitted requirements, unclear or conflicting instructions,
and guidance attached to the wrong entity or declared in the wrong
scope. If the diagnosis supports a guidance change, the developer
revises the relevant instruction and tests again. Failures caused by
other parts of the implementation or system require changes to those
parts.

Identifying missing requirements and diagnosing failures remain
developer judgments; the compiler and runtime provide the binding,
guidance-selection, and prompt-construction mechanisms described in
Section 4. The developer stops revising guidance when the acceptance
criteria are met or the diagnosis does not justify another guidance
change. Remaining issues are recorded for further investigation. As
development continues, requirements may change and some guidance may
become redundant. The developer can update or remove individual
instructions and repeat the testing cycle, without requiring every
entity to be annotated.

Input: Application requirements $`R`$, program $`P`$, test cases
$`\mathcal{T}`$

Output: Updated program $`P`$, test results $`E`$, unresolved observed
issues $`U`$

// Initial enrichment from the specification

1 Compare $`R`$ with the code information, inputs, and existing guidance
supplied to the relevant LLM-guided operations;

2 foreach _requirement identified by the developer as needing additional
guidance_ do

      3 Express the requirement as concise natural-language guidance
$`q`$;

      4 Select the program entity $`e`$ whose meaning or behavior $`q`$
clarifies;

      5 Select the declaration scope $`s`$ where the guidance should
apply;

      6 Add guidance $`q`$ for entity $`e`$ in scope $`s`$ to $`P`$;

// Refinement through testing

7 while _true_ do

      8 Run $`\mathcal{T}`$ on $`P`$ and record results $`E`$;

      9 Compare the decisions and application outcomes with $`R`$,
recording unresolved observed issues in $`U`$;

           11 return _$`(P,E,U)`$_;

      12 Diagnose the differences between observed and intended
behavior;

      13 if _the diagnosis supports a specific change to the guidance_
then

           14 Add, revise, or remove guidance in $`P`$, adjusting its
text, associated entities, or scopes as needed;

      15 else

           16 return _$`(P,E,U)`$_;

Supporting this workflow while retaining automatic prompt construction
leads to the following design requirements for the language mechanism
and its implementation:

1.  (1)
    Dedicated model guidance. Provide a dedicated way to express
    natural-language instructions for the model, allowing developers to
    maintain guidance independently of ordinary documentation.
2.  (2)
    Explicit entity associations. Associate each instruction with the
    program entity it describes, including functions, parameters, types,
    fields, and individual enum members.
3.  (3)
    Scoped guidance. Allow guidance to be declared in the scope
    containing the calls that should use it, independently of where the
    target entity is defined. This allows different workflows to supply
    their own guidance for a shared entity.
4.  (4)
    Preservation during prompt construction. Preserve each instruction’s
    entity association and scope through compilation and execution, so
    that applicable guidance can be selected and placed alongside the
    corresponding code information in automatically constructed prompts.

These requirements motivate Semantic Context Annotations (SemTexts), our
language mechanism for realizing Semantic Engineering. Section 4
presents the SemText syntax and binding rules and explains how the
compiler and runtime implement these requirements.

## 4. SemTexts: Design and Implementation

SemTexts realize the workflow in § 3 by extending MTP with declarations
for application requirements left unspecified by code. Each declaration
associates natural-language guidance with a program entity, while its
declaration scope determines where the guidance applies. The compiler
and runtime use these associations and scopes to place applicable
guidance alongside the corresponding entities in automatically
constructed prompts.

Figure 5 summarizes the compiler and runtime pipeline for incorporating
SemText guidance into generated prompts. The compiler records each
SemText’s target reference, guidance string, and declaration scope in a
SemTable, retaining partially resolved references for later resolution.
For each LLM-guided call site, it combines the relevant code structure
with these bindings in an enriched Meaning-Typed Intermediate
Representation (MT-IR). This representation is preserved through code
generation, making the entity associations and scope information
available at runtime. The runtime then selects the guidance applicable
to the call and combines it with the code structure and current input
values to construct the model’s prompt.

### 4.1. SemText Declarations: Targets and Scope

A SemText declaration associates natural-language guidance with a
program entity using the sem keyword. Its schematic syntax is:

```math
S\rightarrow\texttt{sem}\ T\ \texttt{=}\ Q\ \texttt{;} \tag{1}
```

def standard_workflow(plan: str, feedback: str) -\> AgentType {

return route_revision(plan, feedback);

}

def editing_workflow(plan: str, feedback: str) -\> AgentType {

sem route_revision = "If plan changes are unclear, assume wording-only
and use WRITER.";

return route_revision(plan, feedback);

}

Figure 6. Guidance for a shared routing function declared at module and
workflow scopes. The routing function and return type are defined in
Figure 2(b); the shared enum-member guidance is shown in Figure 3.

Here, $`T`$ identifies the target program entity, and $`Q`$ is a string
literal containing the guidance. The target can be a named declaration
defined in or imported into the program, such as a function, method, or
type, or a named component of such a declaration, such as a parameter,
field, or enum member. For example, $`T`$ can name the function
route_revision, as shown in Figure 6, to associate guidance with that
function.

Where the developer writes this sem declaration determines which calls
can use the guidance attached to $`T`$. For example, to supply guidance
specifically for the call to route_revision inside editing_workflow, the
developer writes the declaration inside that workflow’s function body,
as shown in Figure 6. The declaration names route_revision as its
target, while its lexical scope makes the guidance local to
editing_workflow. The declaration at module scope supplies the default
guidance used by standard_workflow. This allows guidance for a shared
function to be declared within the workflows that use it, separately
from the function’s definition.

To let the runtime select the guidance applicable to each call, the
compiler records each declaration’s target reference, guidance string,
and declaration scope in a _SemTable_, as shown in the green panel at
the lower left of Figure 5. Any unresolved part of a target reference is
retained for resolution when the target is needed at an LLM-guided call
site. § 4.2 explains how these bindings are preserved during
compilation, while § 4.3 explains how the runtime uses them to select
applicable guidance and place it in the generated prompt.

### 4.2. Compiling SemTexts into Enriched MT-IR

#### Recording SemText bindings.

After parsing and symbol analysis, the compiler uses the program’s
symbol table and available import information to resolve each SemText
target as far as possible. It records the resulting target reference
together with the guidance string and the scope containing the sem
declaration. The green panel at the lower left of Figure 5 shows this
recording step. Each resulting binding has the form:

```math
b=\langle s,r,q\rangle, \tag{2}
```

where $`s`$ is the SemText declaration scope, $`r`$ is the target
reference, and $`q`$ is the guidance string. A fully resolved reference
identifies a program entity $`e`$. A partially resolved reference
preserves the information already known about the target together with
the names that still require resolution. The SemTable stores the binding
as $`\Sigma(s,r)=q`$, using the declaration scope and target reference
to identify the entry.

The following rules govern how SemText bindings are recorded and
resolved:

1.  (1)
    Supported targets. A target must name a declaration defined in or
    imported into the program, or a named component of such a
    declaration, as described in § 4.1. Expressions that access
    individual runtime values, such as items\[1\], and attributes
    synthesized through dynamic lookup are not supported targets.
    Generic type applications are also excluded as annotation targets;
    their constituent types are followed during structural construction.
2.  (2)
    Deferred target resolution. An imported type may be identifiable
    before information about its fields is available. A SemText
    targeting one of those fields is retained without requiring complete
    resolution during compilation. When the type or member is needed at
    an LLM-guided call site, the structural information available for
    that call is used to complete the relevant target resolution. A
    declaration whose target is not needed by a call remains recorded
    without contributing guidance to that call. Under the lexical-scope
    rules described in § 4.3, SemTexts declared in an imported type’s
    defining module do not apply to a call unless their declaration
    scope lies on that call’s recorded lexical scope chain.
3.  (3)
    Uniqueness within a scope. Duplicate SemText declarations for the
    same entity in the same scope are rejected, with the check deferred
    when target resolution is incomplete. Declarations in different
    scopes remain separate bindings.

For example, the module-level declaration in Figure 6 and the
declaration inside editing\_-workflow both target route_revision. As
they occur in different scopes, the compiler records separate SemTable
entries, each retaining the corresponding target reference, declaration
scope, and guidance string.

#### Identifying entities for enrichment.

With the SemText bindings recorded, the compiler next uses the called
operation’s structure to identify which bindings may contribute
guidance. This step reuses MTP’s existing structural representation,
denoted $`\operatorname{MTIR}(f)`$ for an operation $`f`$, which
contains its interface and relevant type structure (Dantanarayana et
al., 2025). The entity and type references in this representation
connect the operation’s structure to the bindings retained in the
SemTable.

The compiler follows available type references, including generic type
arguments, to expose relevant types and their named components. This
traversal proceeds whether or not the containing type has a SemText
declaration. When an imported type’s structure is unavailable, its
reference is retained so that expansion can continue when the required
information becomes available for a call.

For route_revision, expanding the AgentType return type exposes PLANNER
and WRITER as separate entities. The subsequent enrichment step can
therefore collect candidate guidance for each member even when AgentType
itself has no SemText declaration. Following the type structure thus
makes guidance on individual components available alongside the
components they describe.

#### Constructing enriched MT-IR

The compiler uses the program entities identified during structural
traversal and the type references retained for later expansion to
collect candidate SemText bindings from the SemTable. For a source call
site $`c`$ invoking operation $`f`$, let $`\mathcal{E}_{f}`$ denote the
entities currently represented in $`\operatorname{MTIR}(f)`$. The
collected bindings are stored in a map $`B_{c}`$, where each entry
$`B_{c}(s,r)=q`$ retains the declaration scope, target reference, and
guidance string.

A binding is retained if its target reference identifies an entity in
$`\mathcal{E}_{f}`$, or if incomplete target resolution or type
information prevents ruling out its relevance to the operation. Bindings
known to be unrelated are omitted. Collection considers all declaration
scopes, so $`B_{c}`$ may contain several candidate SemTexts for the same
entity. These alternatives remain available for runtime selection.

To support that selection, the compiler records the lexical scope
containing the call, $`s_{c}=\operatorname{scope}(c)`$, and its
enclosing-scope relationships, $`\rho_{c}`$. Here, $`\rho_{c}(s)`$ gives
the lexical parent of scope $`s`$, with $`\rho_{c}(s)=\bot`$ when $`s`$
has no parent. The enriched representation is:

```math
\operatorname{MTIR}^{*}(c)=\langle\operatorname{MTIR}(f),B_{c},s_{c},\rho_{c}\rangle. \tag{3}
```

Algorithm 2 summarizes this construction, corresponding to the blue
panel in the lower middle of Figure 5. It first invokes MTP’s existing
structural construction, then collects candidate bindings and records
scope metadata. The predicate
$`\operatorname{MayContribute}(r,M,\mathcal{S})`$ implements the
retention rule above using the available symbol and type information
$`\mathcal{S}`$: it returns true for a target represented in $`M`$ or
one whose relevance remains undetermined.

           5 $`B_{c}(s,r)\leftarrow q`$;

Code generation preserves the enriched MT-IR for runtime lookup. At
invocation, the runtime identifies the calling function or module from
the execution context and locates the corresponding compiled scope
metadata, without traversing the source AST. § 4.3 explains how it
completes any required target resolution and selects guidance from the
retained candidates.

### 4.3. Selecting SemTexts and Constructing Prompts at Runtime

Using the enriched MT-IR and scope metadata located for the current
invocation, the runtime resolves the candidate bindings needed by the
call. As illustrated in the lower-right runtime panel of Figure 5, it
then selects the applicable SemTexts and constructs the model’s prompt
by placing their text alongside the corresponding structural entries and
incorporating the current input values.

#### Resolving candidate bindings.

The compiler-retained bindings have the form $`B_{c}(s,r)=q`$, where a
target reference $`r`$ may still be partially resolved. The runtime
first considers bindings whose declaration scopes lie on the call’s
recorded lexical scope chain. It continues MTP’s structural traversal
where necessary, using the declared type and member metadata of loaded
imported definitions to expand retained type references. Let
$`\mathcal{E}_{c}`$ denote the entities represented in the request after
this expansion.

The runtime resolves candidate references that name entities in this
structure or named components of types reached by the traversal. It
records the resulting bindings in a map $`\widehat{B}_{c}(s,e)=q`$,
preserving each SemText’s declaration scope and guidance string.

As target identities become known, the runtime performs any outstanding
uniqueness checks and rejects duplicate declarations for the same entity
in the same scope. If a candidate reference required by the request’s
structure remains unresolved, the runtime reports a resolution error
before invoking the model. Retained candidates outside the call’s
lexical scope chain or unrelated to its structure do not cause
resolution errors for that call.

#### Selecting applicable SemTexts.

Algorithm 3 defines $`\operatorname{ResolveSem}`$, which selects a
SemText for one entity from the resolved candidate bindings. The
algorithm starts at the call’s lexical scope $`s_{c}`$ and follows the
recorded parent relationships $`\rho_{c}`$. It returns the first
matching SemText, implementing nearest-scope precedence. If no binding
is found along the enclosing-scope chain, it returns $`\bot`$.

Input: Entity $`e`$, call-site scope $`s_{c}`$, resolved candidate
bindings $`\widehat{B}_{c}`$, enclosing-scope metadata $`\rho_{c}`$

Output: Selected SemText string $`q`$, or $`\bot`$

1 $`s\leftarrow s_{c}`$;

2 while _$`s\neq\bot`$_ do

      3 if _$`(s,e)\in\operatorname{dom}(\widehat{B}_{c})`$_ then

           4 return _$`\widehat{B}_{c}(s,e)`$_;

      5 $`s\leftarrow\rho_{c}(s)`$;

6 return _$`\bot`$_;

Algorithm 3 Selecting a SemText for an Entity (ResolveSem)

The runtime applies this procedure independently to each entity
represented in the request:

```math
\Gamma_{c}=\left\{e\mapsto\operatorname{ResolveSem}(e,s_{c},\widehat{B}_{c},\rho_{c})\;\middle|\;e\in\mathcal{E}_{c}\right\}. \tag{4}
```

A result of $`\bot`$ leaves the entity’s structural description without
an additional SemText. This denotes the absence of an applicable
declaration, rather than a failure to resolve its target.

#### Constructing the prompt.

Using the selection results in $`\Gamma_{c}`$, the runtime constructs
the prompt from the operation’s structural entries, their selected
SemTexts, and the current input values. A function’s SemText accompanies
the operation description; a parameter’s SemText accompanies the
corresponding input description; and a SemText for a type, field, or
enum member accompanies that entity’s structural entry. Existing MTP
machinery supplies the surrounding request structure and value
serialization.

The binding and selection rules do not establish precedence between
instructions attached to different entities or resolve contradictions
between them; interpreting the selected guidance remains the model’s
task.

For the calls in Figure 6, the runtime selects the module-level SemText
for route_revision when called from standard_workflow, and the local
SemText for the same function when called from editing_workflow. The
local declaration changes the instruction associated with route_revision
in the editing workflow’s prompt. Because route_revision returns
AgentType, the runtime includes AgentType.PLANNER and AgentType.WRITER
as return options, together with their SemTexts from Figure 3 in § 2.
These SemTexts describe when to select each agent and appear in both
workflows’ prompts. The local declaration in editing_workflow changes
the function’s instruction for handling ambiguous feedback; it does not
change the descriptions of the return options.

### 4.4. SemText Implementation

The implementation extends the Jac compiler and MTP
runtime (Dantanarayana et al., 2025; Mars et al., 2023), adding support
for SemText declarations, scope-aware bindings, and their incorporation
into generated prompts.

#### Compiler integration.

The Jac parser is extended to retain sem declarations in the AST. A
SemTable pass builds on Jac’s existing symbol and import information,
while MT-IR construction adds candidate bindings and scope metadata to
MTP’s structural representation. Code generation preserves this enriched
representation for runtime access. These extensions implement the
compilation procedure described in § 4.2.

#### Runtime integration.

The MTP runtime is extended to access the preserved bindings and scope
metadata and apply the resolution and selection procedures in § 4.3. Its
prompt renderer incorporates selected SemTexts alongside the
corresponding structural entries. Existing MTP components continue to
handle value serialization, model invocation, and response processing.

#### Experimental Setup

We implement SemEng through SemTexts in the Jac programming
environment (Mars et al., 2023; Mars, 2025b; Mars, 2025a), extending the
MTP compiler and runtime to incorporate entity-associated annotations
into generated prompts. Our application experiments use Claude Opus 5.5,
DeepSeek V4.1 Flash, and Gemma 3 27B. For Task Manager and Content
Creator, we use GPT-4.1-mini as an LLM judge under fixed,
application-specific evaluation rubrics.

#### Baselines

We compare four integration approaches.

1.  (1)
    Prompt Engineering (PE). We use traditional prompt engineering, with
    manually written prompts and explicit model calls to integrate LLM
    functionality into the application.
2.  (2)
    Base MTP (Dantanarayana et al., 2025). We use standard MTP, which
    relies on the semantics conveyed by the code to generate prompts.
3.  (3)
    DSPy (Khattab et al., 2023). The same application requirements
    captured by SemTexts are expressed through signature descriptions
    and input/output field annotations, which DSPy incorporates into
    model requests.
4.  (4)
    Semantic Engineering (MTP + SemTexts). We add SemTexts to relevant
    program entities in Base MTP to express application requirements not
    explicit in the code. MTP incorporates these SemTexts into generated
    prompts.

For each application, we ensure that the prompts used by PE, DSPy, and
SemEng provide the model with the same application requirements and task
information. To achieve this, we review the final prompts produced by
these three approaches and sent to the model, both manually and with LLM
assistance. We refine the implementations to include any missing
requirements and verify the revised prompts through both forms of
review.

#### Benchmark Applications

We evaluate SemEng on GSM8K (Cobbe et al., 2021) for mathematical
reasoning and HotpotQA (Yang et al., 2018) for multi-hop question
answering. These benchmarks provide established tasks for evaluating
performance, but do not cover the full range of capabilities we examine
in AI-integrated applications: C1: multimodal perception, C2: tool use
and integration, C3: memory and context management, C4: information
retrieval, C5: multi-agent coordination, and C6: planning and reasoning.
We therefore construct a suite of seven application benchmarks, each
exercising one or more of these capabilities and collectively covering
all six. This suite allows us to examine how SemEng affects application
behavior when model-guided operations interact with tools, application
state, or other agents. Table 1 summarizes the applications, datasets,
evaluation methods, and capability coverage.

### 5.3. RQ3: Cognitive Effort of Semantic Enrichment

To address RQ3:, we examine the cognitive effort required to express
missing application intent using SemEng and PE, with both approaches
aiming to reach the same performance target. RQ1 measures the amount of
integration code and annotations in the final implementation. Prior work
shows that reasoning-token counts predict human response times across
reasoning tasks, linking token consumption to cognitive effort (de Varda
et al., 2025). Motivated by this finding, we use coding-agent token
consumption as an indirect proxy for the effort needed to determine
where and how to express missing intent. We run all approaches with the
same coding agent, model, requirements, and performance target.

#### Experimental Setup

We conduct the experiment on Task Manager and Service Center using
Claude Code with Opus 5.5. We construct the starting implementations
from the applications evaluated in RQ1 and RQ2, retaining their existing
integration code and orchestration. For MTP, we remove all SemTexts
while retaining the application code. For PE, we remove the
corresponding application requirements from the manually written
prompts, retaining the information that base MTP conveys through code
semantics and runtime inputs. Both starting implementations therefore
provide the application model with the same task information. The coding
agent must then express the same additional application requirements
through prompts or SemTexts.

For each application, the coding agent receives the same behavioral
requirements and development tests. We compare three approaches: Prompt
Engineering(Prompt Eng.), which supplies the missing intent through
application prompts; Full SemText Annotation, which adds SemTexts to all
eligible program entities; and Semantic Engineering(SemEngng), which
identifies intent not already conveyed by the code and selectively adds
or refines SemTexts at the relevant entities.

For each application and approach, we repeat the experiment three times
using the same starting implementation and initial instructions. In each
repetition, the agent uses development tests to test and revise its
prompts or SemTexts until it meets or exceeds the existing PE baseline’s
score on those tests. We report the mean and standard deviation of
coding-agent token consumption across the three repetitions. Task
Manager uses DeepSeek V4.1 Flash, with 30 queries available to the agent
as development tests and 50 separate queries reserved for final tests.
Service Center uses Gemma 3 27B, with 41 development tickets and 78
separate tickets reserved for final tests.

Figure 8. Coding-agent tokens consumed to reach the PE baseline’s score
on the development tests. Bars show means over three repetitions, with
error bars indicating one standard deviation. _Prompt Eng._: Prompt
Engineering; _Full Annot._: full SemText annotation; _SemEngng_:
Semantic Engineering.

#### Results

Figure 8 shows that both SemText approaches use fewer coding-agent
tokens on average than PE to reach the PE baseline’s score on the
development tests. SemEng consumes the fewest tokens on both
applications: PE uses approximately $`1.86\times`$ as many tokens as
SemEng on Task Manager and $`1.55\times`$ as many on Service Center.

SemEng also reaches this target with fewer annotations than full SemText
annotation: 7–11 versus 39 on Task Manager, and 11 versus 30–31 on
Service Center. In these experiments, selectively annotating the
entities associated with missing intent is sufficient to reach the
baseline performance, with lower token consumption than annotating all
eligible entities.

On the final tests, SemEng achieves scores close to those of the
agent-authored PE implementations: 80.2% versus 79.6% on Task Manager
and 91.5% versus 92.7% on Service Center. Thus, SemEng uses fewer
coding-agent tokens to reach the development target while achieving
similar observed performance to agent-authored PE on the final tests.

These results suggest that SemEng requires less cognitive effort than PE
to express missing application intent and reach the same performance
target. PE requires locating and revising the relevant prompt segments.
SemEng allows the missing intent to be expressed through SemTexts at the
relevant program entities, while MTP incorporates these additions into
generated prompts. The lower token consumption is consistent with this
structure reducing the effort needed to determine where and how to
express the missing intent.

#### Key Takeaways

1.  (1)
    Lower cognitive effort to add missing intent: The results suggest
    that SemEng requires less cognitive effort than PE to add missing
    application intent and reach the same performance target.
2.  (2)
    Selective enrichment reduces effort: The results suggest that adding
    SemTexts only where intent is missing reaches the same performance
    target with less cognitive effort than annotating every eligible
    entity.

### 5.4. RQ4: Understanding Where and Why Semantic Enrichment Helps

Figure 9. Application structure and cumulative task success for Service
Center using Gemma 3 27B and Task Manager using DeepSeek V4.1 Flash. S1
counts tasks routed correctly. S2 counts tasks that pass both routing

final-reply checks. Every percentage uses the full task set as its

routing and desk SemTexts but no composer SemText.

To address RQ4:, we examine when application requirements are not
sufficiently expressed by code and where SemTexts should be added to
supply the missing intent.

#### Experimental Setup

We evaluate two benchmark applications from Table 1: Service Center with
Gemma 3 27B and Task Manager with DeepSeek V4.1 Flash. For this ablation
study, we select 60 of the 240 Service Center tickets and 60 of the 220
Task Manager queries. We evaluate all configurations on the same sample
for each application, including the MTP baseline (_base MTP_) and Prompt
Engineering (PE) from the earlier experiments. We also evaluate three
additional configurations: _MTP + Docstrings_, which adds one docstring
per relevant function, with enum-selection criteria collected in the
routing function’s docstring; _Full SemText Annotation_, which adds
SemTexts to all eligible program entities; and _Semantic Engineering
(SemEngng)_, which selectively adds SemTexts where application
requirements are not sufficiently expressed by code. We repeat each
evaluation three times and report mean success rates.

Figure 9 shows the workflows and success rates at each stage for Service
Center and Task Manager. For Service Center, Figure 10 shows how final
task success changes as SemTexts are added incrementally, and Figure 11
lists the SemTexts used.

#### Service Center

Service Center resolves customer support tickets in three stages. First,
the router, select_subagent, selects the appropriate desks from seven
available specialists. It returns a list of SubAgentSelection values,
each pairing a specialist from the SubAgent enum with a delegated task.
In the second stage, the selected desks carry out their assigned tasks
using backend tools such as get_payment and issue_refund. Finally,
merge_replies combines their replies into one customer response. A
ticket succeeds only when the backend reaches the expected state and the
reply states the required facts.

Final success is 21.9 percent for base MTP, 85.6 percent after adding
routing annotations, 91.0 percent after adding desk annotations, and
91.2 percent after adding the composer annotation. Full annotation
achieves 64.7 percent and function-level docstrings achieve 36.8
percent.

desk, and composer SemTexts are added cumulatively. Full annotation and
docstrings are separate comparisons; the dashed line shows PE.Final
success is 21.9 percent for base MTP, 85.6 percent after adding routing
annotations, 91.0 percent after adding desk annotations, and 91.2
percent after adding the composer annotation. Full annotation achieves
64.7 percent and function-level docstrings achieve 36.8 percent.

We first compare the routing requirements with the code for
select_subagent and the SubAgent enum. We find missing selection
criteria at both levels. The router’s name and list return type do not
specify one selection per currently requested action or the exclusion of
background information. Within the enum, UPDATE_STATUS can suggest
changing status although its desk only reports it, while CANCEL_ORDER
leaves unclear that cancellation requests should still be routed when an
order may have shipped. Similarly, ESCALATE_TO_HUMAN does not convey
that escalation applies only when no other desk can handle the request
and must be selected alone.

We express these missing requirements through
$`\mathrm{Sem}_{\mathrm{routing}}`$: one SemText on the routing function
and three on the relevant enum members, shown in lines 1–6 of Figure 11.
In MTP + Docstrings, the routing requirements are collected in a single
docstring on select_subagent, including the selection criteria
associated with individual SubAgent enum members. In Figure 9, the
percentage of all tickets routed correctly (S1) rises from 23% with base
MTP to 96% with selective SemEngng, exceeding both PE and MTP +
Docstrings. This result suggests that associating requirements with the
relevant program entities is more effective than collecting them in a
single function-level docstring.

We then compare the second-stage requirements with the code for the
specialist desks. Their tool names and signatures identify the available
operations, but two requirements concerning their replies remain
missing. The status desk must state the status exactly as returned by
its tool, and the escalation desk must tell the customer that a human
agent will take over. We express these requirements through two
function-associated SemTexts, $`\mathrm{Sem}_{\mathrm{desks}}`$, shown
in lines 8–9 of Figure 11. With both $`\mathrm{Sem}_{\mathrm{routing}}`$
and $`\mathrm{Sem}_{\mathrm{desks}}`$, 95% of all tickets are routed
correctly and also pass the desk and tool-action checks (S2) in
Figure 9, exceeding base MTP and PE.

At the third stage, we compare the reply-composition requirement with
the code for merge_rep-lies. Its name, signature, and inputs already
convey that it combines the specialist replies into one customer
response, so we add no composer SemText. With only the routing and desk
SemTexts, 91% of all tickets pass the routing, desk and tool-action, and
final-reply checks (S3) in Figure 9. This final task success rate
exceeds PE’s 79%, as well as the rates achieved by full SemText
annotation and MTP + Docstrings. Thus, annotating all eligible entities
or supplying guidance through function-level docstrings yields lower
final success than selectively adding the six SemTexts.

Figure 10 then examines how final task success changes as SemTexts are
added incrementally. Base MTP achieves 21.9% final task success. Adding
only the four routing SemTexts raises it to 85.6%. Retaining those
SemTexts and adding the two desk SemTexts raises final success to 91.0%.

We also test an additional composer annotation,
$`\mathrm{Sem}_{\mathrm{composer}}`$, shown on line 11 of Figure 11,
which restates the composer’s purpose. Adding it to the routing and desk
annotations changes final success only from 91.0% to 91.2%. Thus, the
largest improvement comes from supplying the missing routing criteria,
followed by the two required reply facts; restating the composer’s
purpose provides little additional benefit.

#### Task Manager

Task Manager illustrates a different location for missing intent. Its
routing enum distinguishes GENERAL_CHAT, TASK_HANDLING, and
EMAIL_HANDLING. In Figure 9, 100% of all tasks are routed correctly with
base MTP, compared with 98% under the selective SemEngng configuration
(S1). The selective configuration adds no routing SemTexts.

The missing requirement concerns email handling: the application must
obtain the user’s approval before sending an email, but the availability
of send_email does not express this condition. SemEngng supplies that
requirement through a SemText while leaving routing and reply
composition unannotated. Under this selective configuration, 98% of all
tasks pass both routing and the required task or email-handling checks
(S2), compared with 72% under base MTP.

Finally, 97% of all tasks pass the routing, task or email-handling, and
final-reply checks (S3) under the selective configuration, compared with
70% under base MTP. The improvement therefore occurs in handling
requests and completing tasks, while routing success remains similar.
Selective enrichment also exceeds full annotation’s 85% final success,
again showing that adding SemTexts to more entities does not necessarily
improve behavior.

#### Key Takeaways

1.  (1)
    Add SemTexts for selection criteria and policies missing from code:
    Making these requirements explicit at the relevant program entities
    can improve task success.
2.  (2)
    Where intent is expressed matters: Associating requirements with the
    relevant program entities through SemTexts can be more effective
    than combining them in a single function-level docstring.
3.  (3)
    Selective enrichment can outperform full annotation: Annotating
    every eligible entity does not necessarily improve task success.
    Additional annotations may provide little benefit or reduce
    performance.

## 6. Related Work

A wide range of approaches integrate LLMs into software through code
generation (Levin et al., 2025; Mündler et al., 2025) and runtime model
calls (Khattab et al., 2023; Dantanarayana et al., 2025; Beurer-Kellner
et al., 2023; Zheng et al., 2024). Our work focuses on runtime model
calls and the application intent that code alone does not express.

LMQL (Beurer-Kellner et al., 2023) supports scripted prompts and
constrained generation, while SGLang (Zheng et al., 2024) focuses on
efficient execution of structured model programs. APPL (Dong et al., 2025) embeds prompts in Python functions, and POML (Zhang et al., 2025)
organizes prompt content through reusable markup components. These
systems structure prompt construction and execution; SemEng focuses on
expressing additional intent through annotations associated with program
entities. DSPy (Khattab et al., 2023) expresses tasks through
signatures, including task instructions and field descriptions, and
supports automatic prompt optimization. MTP (Dantanarayana et al., 2025)
generates prompts from the semantics conveyed by program structure and
runtime inputs. We build on MTP to let developers selectively supply
application requirements not explicit in the code while retaining
automated prompt construction.

TypeChat (Microsoft, ) uses types and comments to guide structured
responses, BAML (BoundaryML, ) attaches descriptions to fields and enum
values, and NVIDIA Object-Oriented Agents (NOOA) (Furgale et al., 2026b)
uses docstrings as agent prompts. SemEng provides a dedicated annotation
mechanism, separate from documentation and schema metadata, that binds
intent to program entities. Declaration scopes determine which
annotations apply to a call, and these associations are preserved in
generated prompts. The natural-language content remains interpreted by
the model.

GEPA (Agrawal et al., 2025) improves prompts through reflection on
execution traces and feedback. This optimization is complementary to
SemEng: GEPA searches for effective prompt content, while SemEng defines
how additional intent is associated with code entities and selected for
model calls.

Automatic docstring generation (Poudel et al., 2024; Yang et al., 2025)
aims to document existing code. SemEng focuses on expressing additional
application requirements. Our evaluation compares how docstrings and
SemTexts associate that information with program entities during prompt
construction.

## 7. Conclusion

This paper presents Semantic Engineering, a methodology for identifying
missing application intent and selectively adding and refining model
guidance. We realize it through SemTexts, which bind guidance to program
entities, with compiler and runtime support for scoped selection during
automatic prompt construction. Our evaluation shows a $`5.46\times`$
reduction in integration LOC relative to Prompt Engineering while
matching or exceeding its task performance in most model–application
settings, reaching up to $`1.83\times`$ its task performance. The
coding-agent study shows lower token consumption to reach the same
development-test targets, while the case studies show that selective
enrichment can outperform full annotation and function-level docstrings.
These findings support expressing missing intent at relevant program
entities and refining it through testing. Future work will explore
automated SemText suggestion and refinement.
